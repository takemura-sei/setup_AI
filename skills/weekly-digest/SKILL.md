# weekly-digest

## 何をするものか

複数の個人プロジェクト（`pokemon_apply`, `pokemon_apply_v2`, `pokebox-V3`, `pokebox-V5`, `typing-game`, `front-test` 等）を横断し、直近1週間のissue / PRの動きを集計してMarkdown形式のサマリを作成するSkill。

- リポジトリごとの「オープン中issue数」「今週クローズしたissue/PR数」「今週作成されたissue/PR数」
- 一定期間（デフォルト2週間）更新のない放置issue・レビュー未対応PRの一覧
- 全体を横断したハイライト（動きが多かったリポジトリ、放置が目立つリポジトリなど）

を1つのMarkdownドキュメントにまとめる。定期実行のRoutine（トリガー）と組み合わせ、生成したサマリを定期配信する運用も想定している。

## 呼び出しタイミング

- 「週次ダイジェストを作って」「今週の進捗をまとめて」と言われたとき
- 「放置issueがないか確認して」など、横断的な棚卸しを依頼されたとき
- 定期実行のRoutine（例: 毎週月曜朝）から呼ばれたとき

## 事前準備: 対象リポジトリの特定

1. 対象リポジトリの一覧をユーザーに確認する。会話やこのリポジトリの直近のやり取りで既に対象が示されている場合は聞き直さない（例: `pokemon_apply`, `pokemon_apply_v2`, `pokebox-V3`, `pokebox-V5`, `typing-game`, `front-test`）。
2. 各リポジトリへのアクセス権があるか確認する。セッションのGitHubアクセスが特定のリポジトリにスコープされている場合、スコープ外のリポジトリは集計対象から外し、「アクセスできなかったリポジトリ」として最終出力に明記する（黙って除外しない）。
3. 集計期間（デフォルト直近7日間）と、放置判定のしきい値（デフォルト14日間更新なし）を確認する。特に指定がなければデフォルト値を使う。

## 集計対象

リポジトリごとに以下を集計する。

| 項目 | 内容 |
|---|---|
| オープンissue数 | 集計時点でのオープンissue総数 |
| 今週クローズ | 集計期間内にクローズされたissue / PR数 |
| 今週作成 | 集計期間内に作成されたissue / PR数 |
| 放置issue | しきい値以上更新のないオープンissue（タイトル・issue番号・最終更新日） |
| レビュー未対応PR | オープンPRのうち、CIが失敗している、またはレビューコメントに応答がないもの |

## 生成手順

1. 事前準備で対象リポジトリ・集計期間・しきい値を確定する
2. リポジトリごとに issue / PR 一覧を取得し、集計対象の各項目を算出する
3. `templates/digest.md.template` を読み、リポジトリ単位のセクションを組み立てる（プレースホルダーは下記）
4. 全リポジトリ分のセクションを集計期間のタイトルの下に並べ、末尾に「横断ハイライト」（動きが多かったリポジトリ・放置が目立つリポジトリの要約）を1〜3行で添える
5. アクセスできなかったリポジトリがあれば、その旨を明記する（黙って除外しない）
6. 完成したMarkdownをユーザーに提示する。ファイルとして保存するか、そのまま出力するかはユーザーに確認する

## テンプレート構成

`templates/digest.md.template` … リポジトリ1件分のセクション雛形。プレースホルダーは単純文字列置換で埋める。

- `__REPO_NAME__` … リポジトリ名（例: `pokemon_apply_v2`）
- `__OPEN_ISSUE_COUNT__` … オープンissue数
- `__CLOSED_THIS_WEEK__` … 集計期間内にクローズされたissue/PR数
- `__CREATED_THIS_WEEK__` … 集計期間内に作成されたissue/PR数
- `__STALE_ISSUES__` … 放置issueの箇条書き（無ければ「なし」の1行）
- `__PENDING_PRS__` … レビュー未対応PRの箇条書き（無ければ「なし」の1行）

## 定期実行との組み合わせ

このSkill自体はRoutine（定期トリガー）を作成しない。定期配信したい場合は、`loop` Skillや `morning` Skillと同様の仕組みで「このSkillを呼び出すRoutine」を別途設定するようユーザーに案内する。設定を代行する場合も、配信先・頻度は必ずユーザーに確認する。

## ユーザー確認が必要な操作

- 対象リポジトリの確定（特に、過去の会話にない新しいリポジトリを含める場合）
- 生成したサマリをファイルとして保存する場合の保存先
- 定期実行Routineとして設定する場合の頻度・配信先

## 制約・注意点

- セッションのGitHubアクセスがスコープされている環境では、スコープ外のリポジトリは集計できない。その場合は「集計できなかったリポジトリ」として明記し、無かったことにはしない
- 「レビュー未対応PR」の判定はCI状態・最終コメント日時からの推定であり、実際に対応が必要かどうかの最終判断はユーザーに委ねる
- 大量のリポジトリ・issueを扱う場合、GitHub APIのレート制限や一覧取得のページングに注意する

## 使用例

```
weekly-digestでpokemon_apply_v2とtyping-gameの今週のダイジェストを作って
```

→ 2リポジトリ分のissue/PR集計と放置issue一覧をまとめたMarkdownサマリが生成される。
